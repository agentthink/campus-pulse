# GitHub 双仓库工作流

## 仓库职责

| 仓库 | 可见性 | 用途 | 内容规则 |
| --- | --- | --- | --- |
| `airguard-draft` | Private | 日常开发、实验、阶段记录 | 接收全部开发提交与中间状态 |
| `airguard-competition` | Public | 比赛正式提交 | 只接收经过确认、可复现的发布快照；不镜像草稿历史 |

## 原则

- 正式仓库不沿用草稿仓库的提交历史，避免把实验过程、未完成说明或临时文件带入公开提交。
- 正式仓库的每个版本必须有：
  - 通过的类型检查与构建；
  - 完整测试 / 场景验证记录；
  - 可回查的 `run_id` 或等价运行证据；
  - 与提交对应的版本号或 Git tag。
- 未确认完成的内容不进入公开仓库。
- 不强制推送公开仓库；发布版本只追加，不重写历史。

## 发布流程

1. 在 `airguard-draft` 完成开发与验证。
2. 确认当前提交通过 `npm run typecheck`、`npm run build`、约定的场景与 Regression。
3. 从已验证提交导出干净快照（不含草稿分支历史），单独初始化发布仓库。
4. 更新版本号、README、发布证据与 `docs/release_evidence.md`。
5. 在发布快照中执行最终验证。
6. 提交、打 tag（例如 `v0.2.0`），再推送到 `airguard-competition`。
7. 记录 tag 与验收证据的对应关系。
